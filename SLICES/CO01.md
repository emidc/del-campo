## 2. Superficie de software

Communication OS vive en `contexts/communication`, con dominio, persistencia y
aplicación propios (D-0063). No importa código de Broker ni lee su esquema.

| Superficie | Resultado observable |
| --- | --- |
| Recepción continua | Un endpoint HTTPS recibe los webhooks de Meta, valida la firma `X-Hub-Signature-256`, guarda la entrega cruda antes de responder 200 y persiste cada mensaje de texto una sola vez por `wamid`. Los tipos que no son texto se registran como recibidos, sin procesarlos. |
| Estados de salientes | Los webhooks de estado (`sent`, `delivered`, `read`, `failed`) actualizan el saliente correspondiente. No asumen una secuencia completa: `read` puede llegar sin `delivered`. |
| UI de conversaciones | Muestra la lista de conversaciones y el hilo de cada una, en orden, con dirección, hora y estado de cada saliente. Los mensajes nuevos aparecen sin recargar a mano. Muestra la hora de la última entrega recibida, para que la UI no aparente estar al día si el receptor dejó de recibir. |
| Responder | Desde el hilo se responde con texto libre. La UI muestra si la ventana de servicio de 24 h está abierta y no deja enviar si está cerrada. El saliente se persiste con el `wamid` que devuelve la API (D-0065); si la API rechaza el envío, la UI muestra el error y no crea el mensaje como enviado. |
| Retención | El payload crudo se borra a los 30 días (D-0065), por un proceso programado. |

Identidad del participante en la UI: nombre de perfil de WhatsApp y los últimos 4
dígitos del `wa_id`, o el BSUID si falta el teléfono. La UI no muestra el `wamid`, porque
codifica el teléfono.

No se fijan en este contrato el framework, las rutas HTTP ni el mecanismo de
actualización (polling o push).

**Sin login propio.** Communication OS está pensado para integrarse más adelante en
Broker OS y usar el login de VS01 (D-0059). Esa integración no ocurre en Q4: se decide al
cierre del trimestre (D-0063). Mientras tanto, la UI no queda expuesta: ver §5.

## 3. Origen de los datos y condiciones de la prueba

- **Número:** el número dedicado de Del Campo, +54 9 261 244-3475, registrado solo en
  Cloud API en la WABA de la app "Del Campo Broker". El número corporativo queda fuera
  de CO01 (PROJECT.md §4).
- **Participantes:** dos personas del equipo de Del Campo, con consentimiento escrito
  previo. Ningún cliente.
- **Contenido:** inventado para la prueba. Ningún dato de clientes, pólizas ni salud
  (R-19). Cada mensaje lleva un marcador `CO01-<código de participante>-<número>` para
  poder contarlo sin leer el resto del texto.
- **Ventana de servicio:** cada día de prueba, el participante escribe primero. Así
  todos los salientes son respuestas de texto libre dentro de la ventana: no hacen falta
  plantillas, método de pago ni verificación del negocio. Las respuestas dentro de la
  ventana no cuentan para el límite de 250 destinatarios.
- **Credenciales:** las carga el owner como variables del despliegue: un token de
  usuario del sistema (no el temporal del panel), el App Secret y el token de
  verificación. Ningún agente las recibe (R-16).

## 4. Criterio medible de éxito

Se exigen todos a la vez:

| Medida | Umbral |
| --- | --- |
| Duración | 72 horas seguidas con el receptor desplegado y suscripto. |
| Volumen | Al menos 50 mensajes de texto en total, con al menos 10 salientes y al menos 10 entrantes de cada participante. |
| Mensajes perdidos | Cero: cada marcador enviado aparece en la base y en la UI. |
| Duplicados | Cero filas repetidas por `wamid`. |
| Orden | El hilo de cada conversación coincide con el orden del teléfono del participante. |
| Latencia de recepción | Mediana de `received_at - wa_timestamp` de los entrantes menor a 10 segundos. |
| Recuperación ante caída | Una caída provocada del receptor (respuesta 500 o deploy caído durante al menos 10 minutos) termina sin pérdidas ni duplicados cuando Meta reintenta. |
| Estados | Cada saliente muestra su último estado conocido. |
| Respuesta desde la UI | Todos los salientes de la prueba se envían desde la UI, y ninguno se envía con la ventana cerrada. |

### Protocolo

1. Antes de empezar, el owner confirma el alta del número dedicado (`status:
   CONNECTED`, `platform_type: CLOUD_API`), las dos suscripciones (`subscribed_apps` y
   el campo `messages`) y el consentimiento de los participantes.
2. Cada participante lleva su propio conteo de marcadores enviados y recibidos.
3. La caída provocada se hace una vez, con aviso, y se registra la hora de inicio y de
   fin.
4. Al terminar, un script del contexto compara los marcadores contra la base y calcula
   los conteos, los duplicados y la mediana de latencia. El informe versionable
   contiene solo códigos de participante, marcadores, conteos y tiempos.
5. Un fallo no se reemplaza ni se borra del informe. Si un criterio no se cumple, CO01
   no se acepta: se documenta y se revisa el alcance con el owner, sin bajar umbrales
   después de medir.

## 5. Despliegue

- **Unidad de despliegue (D-0063):** un proyecto de Vercel propio de Communication OS,
  separado del de VS01, con una base Postgres propia, separada de la de VS01. Ninguno
  usa credenciales ni datos de producción de VS01.
- **Receptor:** desplegado en ese proyecto, con URL estable en un subdominio de
  `delcampobroker.com`. Es request/response, sin proceso always-on (D-0065). El borrado
  por retención corre como tarea programada.
- **UI, solo en local (salvaguarda pendiente de confirmar).** La UI muestra contenido de
  conversaciones (datos personales, R-19) y envía mensajes desde el número dedicado.
  Sin login, publicarla en una URL pública dejaría las dos cosas abiertas a cualquiera
  que tenga el enlace. Por eso la UI corre en la máquina del owner, contra la base de
  Communication OS, y no se despliega. El receptor sí queda público, porque Meta tiene
  que alcanzarlo, y se protege con la firma. Publicar la UI exige antes un login o una
  protección a nivel de plataforma, decididos en un ADR.
- **Aprobación:** el despliegue y la carga de credenciales los aprueba y ejecuta el
  owner (R-13, R-16).

## 6. Non-scope

- Grupos, adjuntos, audio, reacciones, estados de WhatsApp y llamadas.
- Plantillas, mensajes iniciados por la empresa o enviados fuera de la ventana de
  servicio, y campañas.
- Login propio de Communication OS y despliegue público de la UI.
- El número corporativo y cualquier conversación con clientes.
- Integración con Broker OS: ni resolución contra `Party` ni lectura de su esquema
  (D-0063).
- Email (D-0010), coexistencia y bibliotecas no oficiales (D-0065).
- IA, búsqueda de texto y clasificación automática de mensajes.
