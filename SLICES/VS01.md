## 2. Superficie de software

Una app web interna para una persona de la correduría que necesita encontrar una
póliza y abrir su documento sin consultar Zoho durante el recorrido de VS01.

| Superficie | Resultado observable | Referencia canónica |
| --- | --- | --- |
| Búsqueda única | Entrada para los campos enumerados en §65; resultados distinguibles y selección explícita si hay más de un candidato. Estado visible cuando no hay resultados. | `DOMAIN.md` §65; D-0019 |
| Navegación y detalle | Recorrido de §65 con contexto suficiente para distinguir candidatos; navegación organizacional y exposición acotada de historial y motivos según §63. | `DOMAIN.md` §63, §65, §74; D-0034, D-0036, D-0037 |
| Acceso documental | Desde el detalle se abre el destino correspondiente en Drive. Archivo o carpeta se presenta según §47; si el destino es carpeta, abrirla no cuenta como haber abierto el documento objetivo de la prueba. | `DOMAIN.md` §47–49; D-0009, D-0032, D-0040 |
| Excepciones visibles | El recorrido distingue resultado ausente, candidatos ambiguos y problema documental. La falta de vínculo no oculta la póliza; se muestran los conteos documentales sobre el conjunto consultado, con denominador explícito. | `DOMAIN.md` §49, §63, §74; INV-019, INV-022 |

No se presenta un candidato ambiguo como coincidencia inequívoca. La app informa la
fecha del lote que consulta para que sus resultados no aparenten ser datos en vivo de
Zoho. No se fijan rutas HTTP, framework, índices ni algoritmo de ranking en este contrato.

La conciliación asistida se prepara como insumo revisado para T-0017, según D-0032.
VS01 consume ese resultado y muestra los pendientes. No se exige construir un editor
operativo de conciliación ni un workflow de resolución dentro de la app.

## 4. Criterio medible de éxito

Se exigen conjuntamente los umbrales ya respondidos en Q-9:

| Medida | Umbral |
| --- | --- |
| Pólizas objetivo encontradas correctamente | Al menos 19 de 20 casos reales. |
| Resultados incorrectos presentados como coincidencia inequívoca | Cero en los 20 casos. |
| Apertura de vínculos documentales de la prueba | Todos los vínculos incluidos en la prueba abren el destino correcto con el usuario de prueba. |
| Tiempo de búsqueda hasta abrir el documento objetivo | Mediana en VS01 al menos 50 % menor que la línea base comparable. |

### Instrumento y protocolo

1. Antes de medir, una persona autorizada congela una lista de 20 casos reales del lote,
   con consulta inicial, póliza objetivo, documento objetivo y vínculos a comprobar.
   Registra cómo los seleccionó. Los casos representan trabajo habitual; no se eligen
   solo porque ya se sabe que VS01 los resuelve. No se agregan cuotas no aprobadas por ramo.
2. La línea base es el recorrido actual Zoho + Drive. La prueba usa el mismo operador,
   cuenta de Drive, equipo, red y objetivos. Ambos recorridos empiezan autenticados y sin
   el objetivo abierto. Se registra el orden de ejecución, alternando qué sistema se mide
   primero para reducir el efecto de aprendizaje.
3. Un cronómetro mide segundos desde que el operador recibe la consulta e inicia la
   búsqueda hasta que abre y confirma el documento correcto. Incluye navegación dentro
   de carpetas. No se descuentan carga, selección ni correcciones durante el recorrido.
4. Una planilla local registra por caso: código anónimo, resultado esperado validado,
   resultado obtenido, coincidencia falsa inequívoca sí/no, aperturas esperadas y
   comprobadas, tiempo de cada sistema o fallo con motivo, fecha, lote y versión probada.
   Nombres, números de póliza, consultas identificatorias y URLs reales quedan fuera de
   Git, prompts y logs de desarrollo, conforme R-19.
5. Una póliza cuenta como encontrada cuando el operador confirma que es la objetivo;
   abrir otro resultado no cuenta. Un fallo no se sustituye por cero segundos ni se
   elimina del informe de los 20 casos. No hallar ningún vínculo no satisface por vacío
   el criterio documental: cada caso tiene un documento objetivo declarado previamente.
6. Para tiempo se usa el mismo conjunto de casos completados en ambos sistemas, con un
   mínimo de 19 pares. Se publican su cantidad y todos los fallos por separado. Con menos
   de 19 pares, o mediana de línea base igual a cero, no hay medición válida de aceptación.
   Ordenados los tiempos, la mediana es el central, o el promedio de los dos centrales
   cuando la cantidad es par. Se exige:
   `mediana_VS01 <= 0.50 * mediana_base`.
7. Se comprueban todos los vínculos congelados para los 20 casos, incluso si falla la
   búsqueda en uno. Abrir un destino ajeno no es éxito. El informe agregado permite
   recalcular las medianas con códigos anónimos y tiempos, y registra los cuatro
   resultados por separado. Ninguna mejora de tiempo compensa un criterio incumplido.

La planilla se guarda en una ubicación local protegida e ignorada, verificada antes de
usarla. El informe versionable contiene solo códigos no identificatorios, tiempos,
conteos y motivos redactados. No se hace esta prueba durante T-0011.

## 5. Autenticación interna

Se ingresa con cuentas corporativas de Google Workspace, según Q-10. La app exige
sesión válida tanto para páginas como para consultas de datos; una cuenta personal o
una sesión inválida no habilitan acceso. No se habilita registro público.

El User mínimo para T-0012 se referencia en `DOMAIN.md` §53; no se introduce otra
identidad de dominio. El mecanismo de sesión y su asociación con User se concreta en
T-0018, con el ADR exigido por R-05 antes de implementar autenticación. No se elige por
implicación Supabase Auth, cuenta de servicio ni delegación de dominio.

T-0018 debe documentar la población interna admitida y verificar su regla de admisión
antes de usar datos reales. Este contrato no concede acceso a toda cuenta Google ni
asume que un sufijo de email por sí solo sea prueba de identidad.

Q-10 no resuelve Q-15: iniciar sesión en Broker OS y poder abrir un recurso de Drive son
comprobaciones distintas. La autoridad documental se consulta en D-0040. Cualquier
implementación que alcance un disparador de T-0002 debe ejecutar ese spike antes del
acceso correspondiente. Este contrato no redefine esos disparadores, no decide D-0022
ni D-0027 y no sustituye la revisión de autorización por un login.

## 6. Despliegue

La aplicación es web y hosteada; el runtime web sigue D-0014. La base sigue D-0013.
T-0018 prepara la configuración reproducible, variables requeridas sin valores secretos,

y la carga en producción tienen la aprobación prevista por R-13; escribir este contrato
no los ejecuta. El alojamiento o necesidad de un worker no se resuelve aquí.
